# QueryDoctor

**A PostgreSQL query performance analyzer.** Paste a `SELECT` query, get a real `EXPLAIN ANALYZE`
plan, plain-English findings, and deterministic optimization suggestions — no black-box AI in the
analysis path.

```text
SELECT * FROM users WHERE city = 'Mumbai';
```

QueryDoctor shows:

```text
Execution Time     1.9 ms
Planning Time      0.1 ms
Rows Returned      1,012

⚠ Large Sequential Scan on users
   PostgreSQL read 10,000 rows and returned 1,012.

💡 Consider an index on users(city)
   CREATE INDEX idx_users_city ON users(city);
```

## Why

Most beginner portfolio projects are CRUD apps. QueryDoctor is a real developer tool: it answers
"why is my query slow?" using PostgreSQL's own execution plan, not a language model guessing at
performance. Every number shown comes from a live `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` run,
and every recommendation is generated by plain, testable Python logic.

## Features

- Safe, read-only query analysis (validated input + a PostgreSQL `READ ONLY` transaction +
  statement timeout — three independent layers)
- Execution plan parsing into a typed tree, visualized as an indented, color-coded UI
- Six analyzer rules: large sequential scans, filters that discard most rows, dominant-time
  bottlenecks, estimate-vs-actual row mismatches, expensive sorts, and costly nested loops
- A deterministic recommendation engine (including real `CREATE INDEX` suggestions built from the
  filter PostgreSQL reported — never AI-generated)
- Query history, stored per analysis with full plan and issue data
- Query comparison with median-of-3 timing and an honest "no significant difference" verdict
  when a change doesn't actually help
- ~140 automated tests (pytest) covering validation, parsing, every rule, recommendations,
  comparison logic, and the API's error handling
- Fully containerized with Docker Compose (one command starts frontend, backend, and a seeded
  PostgreSQL database)

three containers.

## Getting started

### Option A: Docker (recommended — one command)

```bash
git clone <your-repo-url>
cd querydoctor
docker compose up --build
```

- Frontend: <http://localhost:5173>
- Backend docs: <http://localhost:8000/docs>

The sample dataset (10,000 users, 50,000 orders, 1,000 products, 150,000 order items) loads
automatically the first time.

### Option B: run locally

**Backend**

```bash
cd backend
python -m venv venv
venv\Scripts\activate        # Windows
pip install -r requirements.txt
copy .env.example .env       # then fill in your PostgreSQL password
uvicorn app.main:app --reload
```

**Frontend** (separate terminal)

```bash
cd frontend
npm install
npm run dev
```

**Database** — create it and load the sample data:

```bash
psql -U postgres -c "CREATE DATABASE querydoctor;"
psql -U postgres -d querydoctor -f database/schema.sql
psql -U postgres -d querydoctor -f database/seed.sql
```

### Running the tests

```bash
cd backend
python -m pytest
```

Tests needing a live database (marked `integration`) are skipped automatically if PostgreSQL
isn't reachable; everything else runs without it.

## Example queries to try

```sql
-- Triggers a large sequential scan and an index suggestion
SELECT * FROM users WHERE city = 'Mumbai';

-- No issues: uses the primary key index
SELECT * FROM users WHERE id = 500;

-- Triggers an expensive-sort finding
SELECT * FROM orders ORDER BY total DESC;

-- A join, to see the plan tree with nested nodes
SELECT u.name, o.total FROM users u JOIN orders o ON o.user_id = u.id WHERE u.city = 'Mumbai';
```

## Security considerations

QueryDoctor is a **development/local-testing tool**. Before pointing it at anything beyond a
throwaway database, be aware of:

- **Read-only enforcement is layered, not absolute.** Input is validated against a keyword
  denylist, then every analysis runs inside a PostgreSQL `READ ONLY` transaction that's always
  rolled back. The database itself is the real backstop — the validator alone is not a complete
  security boundary (see [Known limitations](#known-limitations)).
- **Query timeout.** Every analysis has a configurable `statement_timeout` (default 5s) to
  prevent runaway queries.
- **No destructive SQL reaches PostgreSQL uncontrolled**, but a `SELECT` can still call expensive
  or side-effecting functions. The timeout is what actually bounds this.
- **Credentials** are read from environment variables (`DATABASE_URL`), never hardcoded, and
  `.env` is gitignored.
- **History is stored in the same database being analyzed.** A user could query the `queries`
  table and read others' saved SQL. Fine for local use; not fine for multi-tenant production.
- **No authentication.** Anyone who can reach the app can analyze queries and read history.
- **What I'd change before production**: a dedicated PostgreSQL role with only `SELECT`
  permission (defense in depth beyond the transaction), a separate schema/database for
  QueryDoctor's own tables, database migrations via Alembic instead of `create_all`, and basic
  auth or an API key.

## Known limitations

- **Query validation is a keyword filter, not a SQL parser.** It over-rejects on purpose (e.g. a
  literal string containing the word `delete` is rejected) rather than risk under-rejecting.
- **Index recommendations are heuristic.** Built with regex over PostgreSQL's filter text; they
  cover simple equality/range filters and skip anything with `OR`, `LIKE`, or function calls
  rather than risk suggesting broken SQL.
- **Comparison timing is not rigorous benchmarking.** Median-of-3 reduces noise but a real
  benchmark would use many more runs and a dedicated tool like `pgbench`.
- **No database migrations.** Tables are created with SQLAlchemy's `create_all`, which only
  creates missing tables and never alters existing ones.
- **Self-joins can double-tag the plan tree UI**, since issues are matched to nodes by
  `(node_type, relation_name)` rather than a unique node id.
